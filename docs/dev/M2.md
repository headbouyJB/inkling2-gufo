# Milestone M2/M3: fast kernels

Status 2026-11-21, Gufo v0.35.0 (`0260e11`), a Ryzen AI MAX+ 395 (gfx1151, 128 GiB) machine, file `UD-Q4_K_XL` unless noted.
Branch `m2-kernels`. Compute path only: `src/engine.*`, `src/hip/fast.hip|hpp` (new), `src/hip/kernels.hip`
is untouched and stays as the fallback for every weight type without a fast kernel. `runner.cpp` is
untouched. Everything below was measured; what was not is listed at the end.

## Result

| --- | --- | --- | --- |
| decode, 64-token context | 19 tok/s | **40.7** (41.5 with `INKLING2_ACT_FAST=1`) | ~24 |
| decode at 4K / 16K / 32K context | not measured | 38.7 / 36.2 / 33.3 | |
| prefill, 4K prompt | 172-197 tok/s (3.4K prompt) | **1,353** | |
| prefill, 16K / 32K prompt | not measured | 1,295 / 1,242 | ~205 @16K |
| KL vs llama.cpp CPU, 9,300 wiki tokens, batched | 1.47e-3 | **1.48e-3** | |
| KL, same tokens, one token per call (decode kernels) | 1.17e-3 (600 tok) | **1.47e-3** (1.65e-3 with `INKLING2_ACT_FAST=1`) | |
| UD-IQ4_XS: decode / prefill 4K / KL (speeds at step 6) | | 39.3 / 839 / 1.60e-3 | |

Targets: prefill >= 1,000 tok/s at 4K is met (1.35x over); decode >= 45 tok/s is **not** met (40.7; weights
alone need ~15.3 ms of the 24.6 ms per token, see "Where the decode time goes"). Through `gufo serve llm`
(one session, 32K context, non-streaming client, final build): 42.3 tok/s decode, 1,341 tok/s on a 3,437-token prompt,
answers and tool call unchanged from M1 (`tools/smoke.py`).

Bench tool: `inkling2_bench` (`tests/bench/bench.cpp`): fresh session, timed prefill of C wiki tokens in one
`Forward`, then 48 greedy single-token calls (3 warm-up calls for graph capture). Numbers move by about 3 %
between runs on this shared machine (other jobs shared the GPU).

Launch overhead (step 1+2, graph vs. no graph): 29.25 ms/token without the graph (`INKLING2_NOGRAPH=1`) and 29.35 ms with it,
and the same later (41.67 without vs 41.73 tok/s with at step 4): the CPU enqueues the ~1,000 kernels of a step well ahead of
the GPU, so the graph buys nothing today. It is kept because it removes the host enqueue from the critical path
once the kernels get shorter, costs nothing, and `INKLING2_NOGRAPH=1` is the debug fallback. The speed-up
came from fewer and cheaper kernels, not from fewer launches as such.

KL detail (UD-Q4_K_XL, tokens as M1): decode path by position range, final build: 0-1023 1.21e-3, 1024-2047
1.68e-3, 2048-4095 1.28e-3, 4096-8191 1.41e-3, 8192-9299 2.10e-3 (batched: 1.29 / 1.93 / 1.26 / 1.44 / 1.96e-3). With
the per-32 scale the decode path had one outlier (position 5185, KL 0.98) and a mean of 1.80e-3: the activation
rounding is what separates the decode path from the f16-WMMA prefill path (the same tokens through the prefill
kernels one token at a time give 1.33e-3 on the first 4,096). UD-IQ4_XS (fallback kernels for K and IQ types):
1.60e-3 batched, 1.14e-3 decode (600).

## What was integrated

Decode (T = 1), `src/hip/fast.hip`, driven by `Impl::DLayer` / `BuildDecode` in `engine.cpp`:
- One fused Q8_0 GEMV for q | gate | rel | k | v (21 MB, one or three input vectors; `lab` H2), the 24 sink and
  32 + 32 conv-projection rows on a second graph branch (`Tiny`), K/V conv + clip + RMS + f16 KV write in one kernel
  (`KvPrep`), split-K attention with the Q/R clip, tau, sink and output gate inside (`lab/attn`, one main kernel + one
  reduce), o-proj Q8_0 GEMV (K 3072), router (last-block-done top-8), `moe_gu_situ` and `moe_down_sum` for NVFP4 and Q8_0,
  lm_head GEMV with the softcap (Q8_0). Per-expert `.scale` is applied inside.
- The block bookkeeping of the 48 visits is static: blocks live in separate buffers, so the pass boundaries need only two
  small copies; the post-conv + residual of each op is deferred into the next mix kernel.
- Position, token and the session's KV / conv pointers are read from device memory (`d_step`, a 48-entry slot table copied
  from the session before each step), so one HIP graph per attention-split bucket (context <= 2K, 4K, 8K, ...) serves
  every session. Graphs are captured lazily on first use (capture time not measured).
- Everything without a fast kernel falls back to `kernels.hip` inside the same graph: other dense types (K and IQ
  quants, F16/BF16 big matrices) through `Gemm`, other expert types through `MoeGemm` with a device-side counting sort
  (`RouteBuild`) instead of the M1 host round trip. So UD-IQ4_XS works, with the fallback speeds above.
- Activations are int8 per 16 values (plus a residual plane by default), the same W8A8 scheme as llama.cpp's MMVQ but
  finer; the lab kernels used per 32 and no residual (the lab's own note flagged this as the cheap next step).

Prefill (T > 1):
- Dense Q8_0 projections and o-proj through the LDS-tiled f16 WMMA grouped GEMM (`k_gemm4`, 4 waves, BN 64), activations
  converted to f16 once per layer; expert GEMMs through the same kernel with GPU-side expert grouping
  (hist / scan / scatter), gate+up+SITU in one pass and a weighted atomic down. Tile choice by ubatch: BN 32 (T < 1,024),
  BN 64 with 8 waves otherwise. Router: tiled F32 kernel + wave-per-token top-k; loop controllers: tiled gate and apply
  kernels (M1 copied every token row separately, 108 ms of a 540 ms ubatch).
- Flash-style WMMA attention (`attn_prefill`), `kv_write` and `qr_prep` replace the clip / norm / write / naive
  attention / sigmoid chain; the relative-bias table is converted once to f16 `[1024][16]`.
- The ubatch is now 2,048 tokens (`INKLING2_UBATCH` overrides, 16..4096 when written; the current range is 256-4096, multiple of 16). Consequences for the cache work: the SWA rings
  are `1024 + ubatch` = 3,072 rows (was 1,536), `Engine::session_bytes()` accounts for it, scratch grows to about 2 GiB.
  `pass_tokens = engine->ubatch()` in the runner follows automatically.

## Where the decode time goes (64-token context, per step, `INKLING2_NOGRAPH=1 INKLING2_PROFILE=1`)

Before steps 3 and 4 (24.8 ms total): a_in 1.84, proj 6.09, kv+attn 1.31, o-proj + conv 2.06, ffn mix/ctl/norm 1.19,
router 0.71, gate+up 5.73, down + tail 3.82, head 2.08. Weights per token are about 3.7 GB (proj 1.0, o-proj 0.36, MoE
1.85, lm_head 0.49): 15.3 ms at 242 GB/s, so the weight kernels run at about 80 % of the stream limit and the rest
(about 5 ms) is the chain of small dependent kernels (mix, controllers, norms, KV, attention, router) with 3-8 us of
ramp and tail each. The lab variants of GEMV shape (lanes per row, rows per wave, waves per block; `INKLING2_TUNE=p,g,d`
selects 5 alternatives each; `tune.log`) land within 1 % of the defaults for the projection kernel and within 0.5-3 %
for gate+up; four of the five `down` NVFP4 variants are 3-13 % worse. Ideas not tried: prefetching the next visit's weights into the 32 MB MALL during the small kernels, a persistent
megakernel for the small ops, q8 KV (attention is 5.5 ms of the 30 ms at 32K).

Prefill (ubatch 512, 4K prompt, ms per ubatch, sum over 48 visits, before step 5): controls and mix 108, ffn controls 41,
router 21, dense projections + small 56, attention 12-30 (grows with context), gate+up 164, down 96, o-proj 18.
After step 5: 53 / 26 / 14 / 62 / 28 / 164 / 96 / 18 = 475 ms. Gate+up and down (260 ms) run at the lab's numbers;
a 2,048 ubatch lowers them by about a third per token.

## Batched decode (M3)

`Engine::DecodeBatch(span<Session* const>, span<const int32_t> tokens)` is the API entry (up to 4 sessions, one lock).
**Implementation: the sessions run one after the other as graph launches**, so there is no throughput gain yet. The lab
kernels support B = 2..4 over the same weights (`k_gemv<B>`, `moe_gu/down` over the union of experts), which is where a
gain of about 1.6x at B = 2 would come from, but the per-session state kernels (`KvPrep`, attention, conv) and a
B-wide graph were not written. The runner's `max_yield_decode_width` is still 1 and `PlanDecodeBatch` is not used; to use
the entry the runner must collect one token per ready session and call `DecodeBatch` once, then read each session's
`logits()`.

## Also fixed

`tests/text/text_tests.cpp:206` (`StreamDecoder` "invalid sequence is released"): a test bug, not a decoder bug. The
operands of `+` in `s3.Push(a) + s3.Push(F0) + s3.Push(b)` are evaluated in an unspecified order and g++ runs them right
to left, so the pushes ran as b, F0, a (the test saw bytes `f0 61 62`, not `61 f0 62`). The decoder releases `F0`
correctly when the next byte is not a continuation. Fix: sequence the three pushes in separate statements. With g++
15.2 all 8,343 checks pass; before the fix 1 of them failed (the same line).

## Deviations from M1 and caveats

1. `Engine::SetTap` fires only on the batched path; the T = 1 decode path does not call it (`--single --tap` shows
   nothing). Use `INKLING2_SLOWDECODE=1` (T = 1 through the prefill-path kernels) to bisect.
2. Logits for every position (oracle sink) still come from the M1 chunked lm_head (naive GEMM, 64 tokens at a time)
   and a host-side top-64 per position; the oracle's 9,300-token pass takes about 18 s (514 tok/s) including that. A normal
   `Forward` computes only the last position's logits, also with the naive GEMM (once per prompt, not per token).
3. Environment switches (all optional): `INKLING2_NOGRAPH`, `INKLING2_SLOWDECODE`, `INKLING2_SLOWPREFILL`,
   `INKLING2_ACT_FAST`, `INKLING2_UBATCH`, `INKLING2_TUNE`, `INKLING2_PROFILE` (with `NOGRAPH`),
   `INKLING2_PROFILE_PREFILL`.
4. int8 activations make the decode logits differ from the batched path by noise of about 0.1 nat at the top-64
   (`mean |dlogit|` 0.116 either way); greedy decoding can diverge from the prefill path after a few hundred tokens.
5. Dense prefill GEMM needs `rows % 64 == 0` and K in {2304, 3072}; the experts K 2304 / 1152. Other shapes (not in this
   family) fall back to the M1 kernels per layer.

## Not verified

- `--sessions > 1` and concurrent `Forward` / `DecodeBatch` (the engine serialises with one mutex; the decode graphs read
  the session through the slot table, which is the part to test), cancellation, contexts above 32K, bucket changes
  under real sampling beyond the bench's 48-token runs (the 9,300-token `--single` run crosses buckets 2K..16K and is
  clean).
- Quality of generated text beyond the smoke prompts and KL / top-1; no PPL run.
- The D2H copy of the 800 KB logits and the host argmax cost about 0.5 ms of the 24.6 ms per token; the bench includes them.
- GPU timings were taken while other jobs shared the GPU; repeat runs differ by 3 % (e.g. 39.1 against 41.9
  decode at 64 tokens for the same binary).
- Run record: `$WORK_ROOT/n/run/*.log` on the build machine (`bench-*.log`, `*.bin` oracle dumps, `tune.log`).

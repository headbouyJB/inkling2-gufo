# 0.1.3 design: prompt-lookup speculative decoding (and the road to adaptive drafting)

> Paths under `notes/` other than `notes/B-forward-spec.md` (for example `notes/x6c-raw/`, `notes/L-dspark-design.md`) are development notes that are not published in this repository. The numbers this log uses from them are quoted here.

Status: design, 2026-11-23. Host paths are Gufo v0.35.0 (`0260e116`); extension paths are this repo.

## Goal and stages
- **Stage 1 (correctness):** prompt-lookup drafts verified through `Engine::Forward` (prefill kernels). Off by default, greedy requests only. Proves the host contract, masks, rollback and cache interaction. Not expected to be faster; not bit-identical to normal decode (prefill vs decode rounding), so quality is judged by matched-token KL.
- **Stage 2 (speed):** verify rows of one session through the fast decode kernels (multi-row lanes), per-row conv snapshots, GPU argmax for greedy. Target: bit-identical to sequential decode (max |dlogit| = 0, identical greedy text), and no loss on ordinary text (`run.py`/`compare.py`, 5 % / 3 ms).
- **Stage 3 (adaptive draft length):** lookup widen/shrink (27B rule: widen after repeated whole copies, back on a rejection); then the bundled DSpark drafter (`mtp.safetensors`) run in-engine with k ∈ 0..7 from a running acceptance rate (greedy and sampled kept separately) against the measured verify-cost curve, shortening or stopping under batch load.

## Host contract (what Gufo gives us)
- Capability flags in `Descriptor().capabilities`: `multi_token_decode`, `batched_multi_token_decode`, `batched_multi_token_decode_max_width` (`src/ext/text.hpp` ~162). The scheduler then calls `DecodeStep(state, max_tokens, sampler)` / `DecodeBatch(...)` instead of SelectNext/Advance (`text_generation_scheduler.cpp` 612, 1623, 1714). Set all three together (width = sessions, 4); setting only `multi_token_decode` can route a pending selection into DecodeStep, which throws.
- `--speculative` cannot carry `lookup` (closed list in `serve.cpp`); keep refusing real backends (`src/runner.cpp` ~694). The switch is ours: `INKLING2_LOOKUP` (dev) and, for release, a provider option in `extension.json`.
- `gufo/ext/prompt_lookup.hpp` (`PromptLookup<TokenId>`): `BeginRequest`, `Step(pos)` (first step of a request copies nothing), `Extend(history, prompt_only)` (sampled requests: prompt only), `Find(history, tail, minimum, accept_source, require_resume)` → `{start,length}`, `Observe(start, proposed, accepted)`. Minimum match 12 greedy / 24 sampled; Flash-Next requires ≥ 3 copied tokens and caps at `min(max_tokens, room, max_speculative)`; `accept_source` should refuse sources crossing message framing (Inkling: `<|end_message|>` and header tokens). Usage model: Flash-Next `engine.cpp` 1060, 1124, 1217-1243.
- `SpeculativeVerifier` is HIP-target-executor specific; not used. We use `PromptLookup` and `SamplerState` only.
- Sampler: the pool itself `Accept`s returned selections (`text_model_runner.cpp` 1396, 1711), so the runner verifies on a copy (`working = sampler`), accepting per verified row, and publishes only draw state with `sampler.CopyDrawStateFrom(working)` (Flash-Next `runner.cpp` 663-668). Greedy row check: sample row, mismatch → restore RNG; sampled: point-mass q=1, accept if `U < p(token)`, else residual draw published with `DeferSample` (Flash-Next `engine.cpp` 1298-1520, `mtp_sampling.hpp` 100-128).
- `PreviewFirstToken` must equal the first selection of the next DecodeStep (scheduler `CheckPreviewResult`).
- Report: `selections` (≥1 unless stop, ≤ max_tokens, no embedded stop), `lookup_tokens`, `lookup_accepted_tokens`, `draft_tokens`, `draft_accepted_tokens`, `draft_rounds`, `execution_plan`. Metrics appear as `gufo_spec_lookup_*`.
- Cache: the host captures only between DecodeStep calls, so each DecodeStep returns fully committed or fully rolled back; any exception after a Forward → `state.Invalidate()`. `CheckpointPosition` = committed position. Rejected rows lie beyond the committed position, so no capture sees them. That holds only while the sliding-window rings have slack for them: it assumes `ubatch > 255 + (k - kept)` (a ring is 1024 + ubatch rows and a rejected chain writes up to k - kept rows past the kept position). The default ubatch is 2048; `INKLING2_UBATCH` may go down to 256, so with lookup on the runner refuses a value of 263 or less at load (k <= 8). Identity gains `speculative=lookup-v1` when on.

## Engine work
- Forward on 2..k tokens runs the prefill path (`engine.cpp` 1757 takes the fast path only for 1 token); per-row logits via the sink; `s.logits_` = last row.
- Rollback to "kept j of k": KV needs only `pos_` reset (SWA rings are 1024 + ubatch rows; global KV append-only); the loop message banks are per-pass scratch. Conv state (`[6656][3]` per visit, 3.8 MB per session) is updated once per span by `kk::ConvStateUpdate` (`kernels.hip` 428), so Stage 1 snapshots it before the verify (D2D), and on partial accept restores it, resets `pos_` and re-forwards the j kept tokens (one extra short pass, only on partial rejection). New engine API: `SnapshotConv`/`RestoreConv`, `Rollback(pos)`, `SetLogits(row)` — or a single `Verify(session, tokens, sink)` + `Keep(j)` pair.
- Runner-side per-token state (`Block`, `call_prefix`, `answer_done`, via `CommitToken`, `runner.cpp` 528) is simulated on a scratch copy while verifying and committed only for kept tokens; `SelectNext`'s masks (`runner.cpp` 483-521: reasoning-off ban after a header, required-call function names, answer_done/max_context stop, stop tokens) are refactored into a helper applied to every verify row.
- Per-state lookup data in `Inkling2State`: `history` (prompt + generated), `PromptLookup`; history set in Prefill and `PreparePrefixReuse`; `BeginRequest` once per request (`SetPromptContext`); `Clear` on cold/restored start.
- `DecodeBatch`: lanes without a draft go through `Engine::DecodeBatch` together (keeps the 0.1.2 batched speed); lanes with a draft run serially in Stage 1.

## Tests
Stage 1: matched-token KL spec vs non-spec on copy-heavy prompts (should stay ≈1.5e-3 vs reference) and greedy agreement rate; rollback stress (every keep 1..k; logits, conv, pos and next 48 tokens vs a fresh run); masks (reasoning off, required call, answer-only, stop tokens); cache (restore mid-request, prefix reuse, spec step → checkpoint → restore → continue); failure injection after Forward invalidates; preview equality; 2-4 concurrent sessions mixing draft/no-draft lanes; layered-prefill yield with a concurrent verify; lookup counters non-zero on copy-heavy, zero on prose.
Stage 2: bit-identity (max |dlogit| = 0, identical greedy text) at 64 / 4K / 32K and mixed lanes; timing pairs on copy-heavy and ordinary text; graph capture for every width.

## Stage 1 review fixes (2026-11-23)
- **Scheduler path for all traffic.** With lookup on, `multi_token_decode` is advertised, so the scheduler calls `DecodeStep` / `DecodeBatch` for every request, sampled ones included. A request without a draft (sampled, a short budget, no match) takes `FinishPlain` or the plain lanes of `DecodeBatch`: the same arithmetic as `SelectNext` + `Advance`, but a different code path from a lookup-off server.
- **Conv snapshot in the resource claim.** `Engine::Create(..., lookup)` records that sessions carry a snapshot; `NewSession` allocates it and adds it to the session's bytes, and `session_bytes()` (the `ResourceClaim` per-request bytes) counts it (3.8 MB a session). With lookup off nothing is allocated or counted. `SnapshotConv` throws on a session without one; the session's byte count never changes after creation.
- **`VerifyChain` invalidation.** The snapshot is taken before the `try`: it only reads the session, so its failure leaves the device state valid and the state is not invalidated. Everything from the verify `Forward` on invalidates on failure. The conv copies run on the engine stream (`hipMemcpyAsync` + a stream sync), like the passes that read and write the history.
- **No draft behind a framing anchor.** When the anchor is message framing or closes the answer block (`answer_done`), nothing is copied behind it.
- **Tests** (`tests/lookup/lookup_test.cpp`; modes `agree reject rollback batch masks maxctx yield`, `--lookup 0` as a control run). A test-only chain hook (compiled only when the lookup test target is configured: `INKLING2_TEST_HOOKS`, `src/runner_test.hpp`) overwrites draft token j of a verify chain so partial accepts run end to end; every step is checked against the host contract (selection count, no stop selection, accepted <= proposed, `PreviewFirstToken` equality). Agreement rule: identical, or a first divergence at or after `--min-agree` tokens (default 64). `tests/lookup/serve_lookup.sh` plus `serve_lookup_client.py` run the server-level comparison (cache hit after a partial accept, two concurrent sessions, tool call, reasoning off, `/metrics` counters) for the GPU step.
- **Yield.** The engine releases its lock and spills the live activations around a layered-prefill yield (`MaybeYield`), so a verify of another session can run inside the callback; the `yield` mode does exactly that (`SetPrefillYield` groups 16, session A drafting inside session B's prefill).


## Stage 2 as built: multi-row decode launches (2026-11-23, not yet run on the GPU)
Drafts are verified through the fast decode kernels instead of the prefill kernels, so the logits of every verify row are meant to be bit-identical to sequential decoding (max |dlogit| 0, identical greedy text), and a partial accept needs no second pass. Default with `INKLING2_LOOKUP=1` on an engine with fast kernels for every layer; `INKLING2_LOOKUP_PREFILL_VERIFY=1` keeps the Stage 1 path for A/B runs (identity text `lookup-v1`; the rows path writes `lookup-v2`).

- **One launch, R rows.** `Engine::DecodeRows(lanes)` runs up to `kMaxRows` = 8 rows in one graph launch. A lane is one session with 1..8 consecutive tokens (anchor + draft); a lane of one token is a plain decode lane. With lookup off the launch is the classic one of 0.1.2 (`DecodeN`, same kernels, same graphs). With lookup on, every launch of two or more lanes runs the per-row path, plain-only batches included (`Engine::DecodeBatch` routes them there; see the Stage 2 review fixes), so a lane's logits never depend on whether a neighbour drafted. Only a single plain lane takes `DecodeN` (its bucket is its own row's).
- **Why each row equals a lone decode.** The batched kernels already compute every token with its own accumulators and its own (token, expert) pairs, so a row's result does not depend on the other rows. Two things did depend on the launch and are now per row: (1) the global-attention split size and count come from the context bucket (`BucketCtx(max position)`), so a launch whose rows span two buckets would split a row differently from its lone decode; with `RowInfo` every row splits by the bucket of its own position (`chunk`, `nsplit` in a per-row device array; the grid is that of the largest bucket, rows with fewer splits leave early, `decode_reduce` reduces its own count). (2) The conv history of a session is read and written in place by each token; rows of one session chain instead: row m reads the committed history for the inputs before the launch and the raw inputs (post-projection K / V, o-proj output, the summed expert rows) of rows m-1, m-2, m-3 of the same session for the rest. They are the same floats the sequential decode would have stored, and the arithmetic is the same expressions, so the result is identical. Kernels: `conv_resid_elem_mr`, `conv_resid_block_mr` (the mix prologue; `k_mix<true>`), `k_kvprep<true>` in `src/hip/fast.hip`; the classic `attn_decode` / `decode_reduce` gained a runtime `rows` branch (null for the classic launch) with identical arithmetic, and the `<false>` instantiations of the mix and kvprep kernels are the old code.
- **Per-row snapshots.** A multi-row lane writes the state after row j to `conv_snap_[j]` (`[48 visits][6656][3]`); the session's own conv slot and `pos_` are not touched. `Engine::CommitRows(s, keep, last_row_logits)` copies region keep-1 into the 48 slots and advances `pos_` by `keep` (rollback = a different row, no re-forward). A lane of one row is updated in place as before. KV rows beyond the kept ones stay in the buffers past the position (same ring-slack argument as Stage 1; a chain is at most 8 rows).
- **Memory.** The snapshot is 8 regions per session: 8 x 3.83 MB = 30.7 MB (Stage 1: one region, 3.83 MB), allocated at `NewSession` and counted in `session_bytes()` (lookup on only). The decode buffers (`[token][...]`) grow from 4 to 8 rows when lookup is on (about 60 MB more with the attention workspace); with lookup off nothing changes.
- **Dense GEMVs for 5..8 tokens.** `k_gemv` and `k_gemv_multi` (one input) are instantiated for 5..8 tokens (LDS 46 KB, 61 KB at K = 3072). The three-input projection of the global layers (64 KiB LDS limit) runs 5..8 tokens as groups of three. Tokens are independent in these kernels, so any grouping gives the same results; the bench verifies it.
- **Graphs.** Key = context bucket * 32 + rows * 2 + multi (the old `ctx * 8 + n` collided above 7 rows). The multi-row graph depends only on (bucket, rows): the row layout, positions, slot tables and snapshot pointers are device data written before every launch (`d_rowinfo`, `d_step`, `d_tbl`). Widths 2..8 at the 2048 bucket are captured at engine creation (lookup on); other buckets on first use (a lazy capture per (bucket, width): the first launch of a width at a new bucket pays one graph capture), with the eager fallback as before.
- **Runner.** `VerifyRows` / `RunRowsStep`: chain = rows of one lane (draft cap 7, since the anchor is a row); `DecodeBatch` puts plain lanes and drafted lanes into one launch when the rows fit in 8, otherwise it deals the spare rows to the drafts one at a time (a prefix of a draft is a valid draft; a lane left with none is a plain lane). Verification (`AcceptRows`), the mask logic, sampler copy and `lookup.Observe` are shared with the Stage 1 path.
- **Not done:** on-GPU argmax (the masks apply per row before the argmax, so it would not be the same selection; R x vocab floats go to the host, about 0.6 MB per row), adaptive draft length (Stage 3), the verify-cost numbers (the GPU step measures them: `inkling2_bench --rows`).
- **Tests.** `inkling2_bench --rows R,... [--verify] [--lanes N,N,...]` (launch time per R at 64 / 4096 / 32000; bit-identity of R rows, of commits of R and R/2 rows and of the next four tokens against sequential decode, including the bucket edges 2044 / 4092 / 32764; mixed launches), `inkling2_lookup_test` (default = Stage 2 requires identical texts and max |dlogit| 0; `--old-path` = Stage 1 rules; `--mode speed`), `x5/drive-x5c.sh` on the lab box.

## Stage 2 review fixes (2026-11-23)
- **Lane composition.** The classic batched launch splits global attention by the bucket of the LARGEST position of the batch, the per-row launch by each row's own. The runner used the per-row launch only when some lane drafted, so with lookup on a plain lane's logits depended on whether a neighbour drafted (for example lanes at 1.5K and 10K context). On an engine created with lookup, `Engine::DecodeBatch` now sends every batch of two or more sessions through the per-row launch (`DecodeRowsN`, one row per lane), and `DecodeRows` does the same for plain lanes; only a single plain lane keeps `DecodeN` (its bucket is its own). Lookup off is untouched (0.1.2). Exception: with a non-zero `INKLING2_TUNE` (`rows_capable()` is false) the runner falls back to the Stage 1 verify and its batches use the classic `DecodeN` launch, so the composition independence above holds for the rows path only. Cost: the per-row launch for B plain lanes against the classic one is measured by the driver (`bench --batch 2,3,4`, with and without `--lookup`; `x5/drive-x5d.sh`).
- **Test that can see a misplaced KV write.** The rows `--verify` reference decoded on the same session and rewound only conv and position, so the correct KV rows the reference left behind hid a misplaced write. Before every launch the KV rows `[pos0, pos0 + n + 4)` are now overwritten with the KV of junk tokens (sequential decode, then conv and position rewound); `lookup_test --mode rollback` does the same. A ring-wrap case (`ring_rows - 2`, 3070 by default: a launch of 5..8 rows straddles the sliding-window seam) joins the bucket edges 2044 / 4092 / 32764. `--bctx 1500,10000 --verify --lookup` compares a plain batch with lanes in different buckets against single-token decode, and `lookup_test --mode bucket` requires every lane of such batches (plain and drafting neighbours) to produce exactly the text of its own plain decoding.
- **Nits.** The debug tap buffer is sized by `kMaxRows`; `rows_capable()` is false when `INKLING2_TUNE` selects a non-zero projection variant (those exist only for 1..4 tokens, so the runner falls back to the Stage 1 verify); `conv_snap_valid_` / `rows_pending_` are cleared before the launch; `static_assert(Engine::kMaxRows == Impl::kMaxRows)`; the classic `attn_decode` / `decode_reduce` gained a runtime `rows` branch with identical arithmetic; graphs are captured lazily per (bucket, width).

## Stage 3a: adaptive draft length for prompt lookup (2026-11-23, not yet run on the GPU)
Goal: choose the number of draft rows per step to maximise expected tokens per millisecond, instead of a fixed cap of 7. The policy (`src/lookup_policy.hpp`, header only, unit test `tests/lookup/policy_test.cpp` on the CPU) changes speed only: the kept tokens are those of plain decoding whatever it chooses, so the text stays identical.
- **Cost model.** `CostTable`: per context (64 / 4096 / 32000, interpolated linearly in log2 of the position of the deepest lane, clamped) the median time of a launch of R = 1..8 rows of one session, plus `extra`, the added time of each further session of a batch. Seeds are the Stage 2 measurements (`notes/x5c-raw/rows-time.out`); R = 5 and 7 were not measured and are the mean of their neighbours; `extra` is the mean over B = 2..4 of (aggregate classic batch step - the same number of rows of one session) / (B - 1) from `reg-speed-off.out`: 3.3 / 5.1 / 2.7 ms at the three contexts. No timing in the decision path. `inkling2_bench --rows ... --costs FILE` re-measures the table (the driver does) and `INKLING2_LOOKUP_COSTS=FILE` loads it (format: `ctx N r1..r8 extra X`).
- **Acceptance.** Per request `Acceptance`: decayed counts (factor 0.75 per round, a window of about four rounds) of tokens tried and accepted, with a prior of 2 pseudo-tokens at 0.8 that decays the same way. A round that proposed k and kept j tried j + (j < k) tokens. The estimate is clamped to [0.02, 0.98]; after a round that was accepted completely the miss rate is halved for the next choice (copies are all-or-nothing). Reset with the lookup index (request start, cold start, restore, prefix reuse). **Decline:** the estimate only moves in `Observe`, which runs only after a draft, so once a run of misses had pushed it below the break-even (about 0.2 at 1.3K, 0.46 at 32K) and the policy picked k = 0, nothing would move it again and lookup stayed off for the rest of the request. Whenever a copy existed and got k = 0 (`ChooseDrafts`, batch lanes without rows included) `Acceptance::Decline()` ages the counts and the prior by one round (counts x 0.75, prior / 0.75 up to its starting weight, the whole-copy bonus forgotten). After 3 misses lookup is drafting again after 1 declined copy at 1.3K and 4K and after 3 at 32K (`policy_test`); a probe that misses goes off again the same way. Chosen over a forced k = 1 probe after N declines: no second counter and no arbitrary N, and how long it stays off follows how bad the misses were. Cost: on text where a copy is found every step and never matches, about one probe (+6 ms at 1.3K) per 2 to 3 steps.
- **Width limit (27B rule), revised.** A fresh request may draft up to 7; after a whole copy it doubles (up to 7). After a rejection the first cut shrank to j + 1 (`classic`), which restarted at 1 after a break with nothing kept and ramped 1, 2, 4, 7: three extra launches per one-token break (`x5d-raw/log-sample-mixed.out`, positions 1317-1327), on top of the estimate that has already dropped (0.98 to 0.72): a double penalty, and the likely cause of adaptive losing to fixed 5 on mixed-breaks (-4 % with the seed table, up to -9 % with the measured one). The default was `floor3` for a while: max(j + 1, 3), so a break costs at most one ramp step (3, then 6 to 7) and the estimate does the rest; `none` (no limit, the estimate alone) and `classic` stay selectable with `INKLING2_LOOKUP_LIMIT=classic|floor3|none` for the A/B (`drive-x5e.sh` runs all three, seed and measured table). Chosen by reasoning, not measured: a three-token floor keeps some protection against runs of diverging copies in noisy text (where the estimate is low anyway and the policy drafts little), without charging a one-token break three launches.
- **Choice.** `E(k) = (1 - a^(k+1)) / (1 - a)` (the anchor counts); for a copy of L tokens, k in 0..min(L, limit) maximises `E(k) / cost(k + 1 rows)`; k = 0 is the plain step (nothing is observed). Minimum copy: sources must offer 3 tokens (`kMinCopy`, the source filter, for both policies; a 1-token source would let the most recent candidate win a tie on match length with a 1 to 2 token continuation over an older one offering 7). A chain shorter than 3 comes only from the cap (`max_tokens`, room, fixed cap), the width limit or the policy. A fixed cap of 1 or 2 filters on min(3, cap) (it silently disabled lookup before).
- **Batch.** In `DecodeBatch` all live lanes are allocated jointly (`Allocate`): drafts are ranked by their marginal expected tokens `a_i^d` (equal marginal cost: one more row), and the number m of drafts taken (the best m, within `kMaxRows - lanes`) maximises `(lanes + sum of the gains) / cost(lanes + m rows, lanes sessions)` with the deepest lane's context; m = 0 (all plain) is a candidate, so drafts that cost the whole batch step more than they return are not added. One lane is the single-lane choice above.
- **Switches.** `INKLING2_LOOKUP_FIXED=<1..7>` restores Stage 2's fixed cap (1 and 2 included) (and its round-robin dealing); `0` or unset is adaptive. The Stage 1 prefill verify (`INKLING2_LOOKUP_PREFILL_VERIFY`) keeps its fixed chain. `INKLING2_LOOKUP_LOG=1` prints one stderr line per round (position, a, copy length L, limit, k, kept; a plain step the policy chose is marked; under the fixed policy a and limit print `-`).
- **Tests.** `lookup_test --mode adapt` runs plain, adaptive, fixed 7 and fixed 5 (and adaptive with a measured table) in one process over copy-heavy, ordinary, mixed-breaks (a deterministic break about every 20 output tokens) and 2..4 lane batches, alternating rounds, every text identical to plain decoding. Plain batches are timed the way the scheduler runs them with lookup off (select per lane, one `AdvanceBatch`), not through the base class's serial `DecodeBatch` (which read about 45 tok/s at batch 4 instead of about 86). Adaptive runs under each limit rule (classic, floor3, none), with the seed and the measured table, next to fixed 7 and 5. `reject` runs twice: as configured (identity, accepted <= j - 1, forced rounds) and on a dedicated fixed-7 runner (anchor-only rounds and at least four partial-accept lengths); the forcer picks j relative to the chain. Risks: the cost table is a model (an R = 7 launch is probably cheaper than the interpolation says, and mixed-context launches were never timed); the break-even of short drafts depends on how much of the 21 ms launch they share, which only the A/B shows.

- **Update after the x5e A/B (11-23).** The measured cost table (`notes/x5e-raw/cost-measured.txt`) is the built-in default (`CostTable::Seed()`), and the default width limit rule is `none`: the A/B put copy-heavy at x2.27, mixed-breaks at 89.3-89.9 tok/s (fixed 5: 85.9-86.5), batches of 2 and 3 at +8-13 % and +8-10 %, batch 4 at +0.8-3.1 % (the old seed table: -1.8 %). `INKLING2_LOOKUP_LIMIT=classic|floor3|none` and `INKLING2_LOOKUP_COSTS=FILE` stay for A/B runs.
